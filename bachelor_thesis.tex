\chapter{Introduction}
\label{chap:introduction}

Large language models (LLMs) have rapidly evolved in recent years from
conversational assistants into capable agents that can reason, plan, and take
actions in the real world~\parencite{brown2020gpt3,yao2022react}. This shift
has been made possible by the ability to give LLMs access to external
\textit{tools} --- functions that let a model query a database, call an API,
or manage infrastructure, all in response to a natural language request
(Chapter~\ref{chap:ai-mcp} describes this agentic paradigm in detail). As
the need for such integrations grows, a key challenge emerges: how do
different AI hosts and models connect to the ever-expanding set of tools and
data sources in a consistent way?

Anthropic introduced the Model Context Protocol (MCP) in November
2024~\parencite{mcp-announcement} to address exactly this problem. MCP is
an open standard that defines how AI applications connect to external tools
and data sources through a client-server architecture (see
Section~\ref{sec:mcp}). Instead of each AI host maintaining its own
integrations, any MCP-compatible host (Cursor, Claude Desktop, or a custom
agent) can connect to any MCP server and immediately gain access to the
capabilities it exposes. This has already led to a growing ecosystem of MCP
servers for services ranging from databases and file systems to cloud APIs
and developer tools.

Red Hat OpenShift AI (RHOAI)~\parencite{rhoai-docs} is an enterprise machine
learning platform built on top of Red Hat
OpenShift~\parencite{openshift}, which is based on
Kubernetes~\parencite{kubernetes-docs}. One of its core features are
workbenches --- containerised JupyterLab~\parencite{jupyterlab} environments
that data scientists and engineers use for model training and experimentation
(Chapter~\ref{chap:rhoai} explains the platform architecture). Managing
clusters with many workbench instances can be a tedious and error-prone task,
currently requiring navigation of the RHOAI web UI or direct manipulation of
Kubernetes resources. The goal of this thesis is to eliminate that problem by
allowing users to manage their workbenches entirely through natural language
--- simply describing what they want to an AI agent, which then carries out
the necessary operations on their behalf.

To achieve this, the thesis presents the design and implementation of an
MCP server that connects AI agents to RHOAI (Chapter~\ref{chap:analysis}
derives the requirements and architecture; Chapter~\ref{chap:implementation}
describes the implementation). The server covers the full workbench
management lifecycle --- from creation and configuration to monitoring and
deletion --- and operates in a safe read-only mode by default to prevent
accidental modifications. It also explores all three capability types that
the MCP standard offers (tools, resources, and prompts), demonstrating how
they can work together in practice. Because RHOAI is currently transitioning
to a redesigned workbench architecture
(Kubeflow Notebooks~2.0~\parencite{notebooks-v2}), the implementation serves
as a proof of concept: it validates the feasibility of the approach and
establishes the architectural patterns and evaluation methodology that a
future production-ready server can build upon
(Chapter~\ref{chap:conclusion} discusses this future work). The complete
source code is available as open source under the Apache License~2.0~\parencite{mcp-server-rhoai-repo}.

\chapter{Background: Artificial Intelligence and the Model Context Protocol}
\label{chap:ai-mcp}

This chapter introduces large language models and the agentic paradigm of tool
use, then describes the Model Context Protocol in detail.

\section{Large Language Models and AI Assistants}
\label{sec:llms}

At the core of modern AI assistants are \textit{large language models}
(LLMs) --- neural networks trained to predict and generate text by learning
statistical patterns from vast amounts of data. The dominant architectural
foundation for LLMs is the \textit{Transformer}, introduced by Vaswani et
al.\ in 2017~\parencite{vaswani2017attention}. The Transformer's
self-attention mechanism allows the model to relate every token in a
sequence to every other token, enabling it to capture long-range
dependencies in text far more effectively than earlier recurrent
architectures. Another benefit of the Transformer is that it is parallelizable,
making it possible to train large models on extensive datasets in a reasonable
time.

Modern LLMs are trained in two main stages. In the first stage,
\textit{pre-training}, the model is exposed to hundreds of billions of
tokens of text and learns to predict the next token in a sequence. This
process, while deceptively simple, causes the model to internalise broad
world knowledge, reasoning patterns, and linguistic structure. In the second
stage, the pre-trained model is fine-tuned to behave as a helpful assistant,
typically through a combination of supervised instruction fine-tuning and
reinforcement learning from human feedback
(RLHF)~\parencite{ouyang2022rlhf}. The result is a model that responds to
natural-language instructions in a coherent and useful way.

The products of this pipeline --- systems such as OpenAI's
ChatGPT~\parencite{chatgpt}, Anthropic's Claude~\parencite{claude}, and
Google's Gemini~\parencite{gemini} --- are commonly referred to as \textit{AI
assistants}. An AI assistant takes a user's message as input and produces a
textual response. It is fundamentally \textit{stateless} and
\textit{passive}: it answers questions, drafts documents, and explains
concepts, but it does not take actions in the world, does not maintain
persistent memory across sessions (by default), and cannot access
information beyond its training data or the content of the current
conversation. This passivity is the key limitation that the agentic
paradigm, described in the next section, overcomes.

\section{AI Agents and Tool Use}
\label{sec:ai-agents}

Despite their broad capabilities, pure language models are isolated from
the external world --- their knowledge does not extend beyond their training
data, they cannot query other systems, and they cannot take actions. The
concept of an \textit{AI agent} overcomes these limitations by equipping a
language model with \textit{tools} --- callable functions that the model can
invoke to interact with external systems, retrieve fresh information, or
modify state. Agents can also be given \textit{memory} --- the ability to
retain information across steps or sessions~\parencite{zhang2024memory}.
Memory can range from simply keeping the full conversation history in the
model's context window to reading and writing records in an external
database via dedicated memory tools.

The key mechanism enabling agent behaviour is \textit{tool calling} (also
known as \textit{function calling}). When a model is given a set of tool
definitions alongside a user request, it can --- instead of producing a plain
text response --- output a structured call to one of those tools, specifying
the tool name and the required arguments. The host application intercepts
this call, executes the corresponding function, and feeds the result back
into the model's context, after which the model continues its reasoning.
This loop can repeat multiple times within a single interaction, allowing the
model to chain tool calls to complete complex, multi-step tasks.

Yao et al.\ formalised this pattern in \textit{ReAct}~\parencite{yao2022react},
which unifies \textit{reasoning} and \textit{acting} into a single loop:
the model first produces a chain-of-thought reasoning trace --- thinking
through what it knows and what it needs --- and then selects and executes an
action (a tool call). The output returned by the tool becomes part of the
context for the next reasoning step. This structured loop gives agents a
degree of \textit{autonomy}: given a high-level goal, an agent can decompose
it into sub-tasks, select appropriate tools, and adapt its behaviour based on
the results it receives.

The practical impact of tool use is significant. An agent equipped with the
right tools can list resources in a Kubernetes cluster, query resource
consumption metrics, and delete workbench instances --- all in response to a
single natural-language instruction such as \enquote{delete workbenches
running for more than a week}. The Model Context Protocol provides a
standardised way of exposing those capabilities to any AI host.

\section{The Model Context Protocol}
\label{sec:mcp}

The Model Context Protocol (MCP) is an open standard that defines how AI
applications connect to external tools and data sources. This section
describes the protocol's motivation and architecture
(Section~\ref{subsec:mcp-overview}), its three main components
(Section~\ref{subsec:mcp-clients-servers}), the capabilities exposed by
clients (Section~\ref{subsec:mcp-client-capabilities}) and servers
(Section~\ref{subsec:mcp-primitives}), and the available transport
mechanisms (Section~\ref{subsec:mcp-transport}).

\subsection{Protocol Overview}
\label{subsec:mcp-overview}

MCP was introduced by Anthropic in November
2024~\parencite{mcp-announcement} to address a fundamental integration
challenge. Its core motivation is the \textit{M$\times$N integration
problem}: without a shared standard, connecting $M$ AI hosts to $N$
external services requires up to $M \times N$ custom integrations, each
with its own authentication, serialisation, and error-handling logic. MCP
reduces this to $M + N$ by providing a single protocol that both sides
implement once.

The protocol is \textit{transport-agnostic} and message-based, built on top
of JSON-RPC~2.0~\parencite{jsonrpc-spec}. Official SDKs are available for
Python, TypeScript, Go, Java, Kotlin, and
C\#~\parencite{mcp-github}.

\subsection{MCP Components}
\label{subsec:mcp-clients-servers}

The MCP architecture defines three main components: \textit{hosts},
\textit{clients}, and \textit{servers}.

A \textbf{host} is the AI application that the end user interacts with
directly --- for example Claude Desktop, Cursor, or a custom agent
application. The host is responsible for managing the user interaction,
sending messages to the LLM, orchestrating tool calls, and processing the output of the LLM.

A \textbf{client} is a component that lives inside the host and manages
exactly one connection to one MCP server. A single host can run multiple
clients simultaneously, each connected to a different server, giving the
agent access to multiple sets of tools at once. The client speaks the MCP
protocol on behalf of the host --- it sends requests to the server, receives
responses and notifications, and forwards results back to the LLM context.
Beyond handling requests, clients can also expose their own capabilities
to servers, enabling server-initiated interactions described in
Section~\ref{subsec:mcp-client-capabilities}.

A \textbf{server} is a lightweight process that exposes capabilities (tools, resources, and prompts) to
clients~\parencite{mcp-spec}. A server typically wraps one specific external system --- a database,
a cloud API, a file system, or a cloud platform. It contains the actual implementation of each capability.
When a tool is invoked, the server executes the corresponding logic and
returns the result. The server does not communicate with the LLM directly --- it only
communicates with the client that is connected to it. This separation of
roles means that server authors do not need to know anything about which
LLM or host will use their tools and other capabilities.
The server-exposed primitives are described in
Section~\ref{subsec:mcp-primitives}. Figure~\ref{fig:mcp-architecture}
illustrates these relationships.

\subsection{Client Capabilities}
\label{subsec:mcp-client-capabilities}

While servers expose tools, resources, and prompts, clients can expose
their own capabilities back to servers, allowing servers to initiate
certain interactions rather than only responding to them.
MCP defines three such client capabilities~\parencite{mcp-spec}.

\textbf{Sampling} lets a server ask the client to generate an LLM
completion on its behalf. This enables servers to perform agentic
sub-tasks --- such as summarising a result or deciding a next step ---
without needing direct access to any language model.

\textbf{Roots} allow a server to query the client about the filesystem
or URI boundaries it is permitted to operate in, so that servers
respect the scope defined by the host environment.

\textbf{Elicitation} lets a server request additional information from
the user through the host, for example asking for a confirmation or a
missing parameter before proceeding with an operation.

\subsection{Server Capabilities}
\label{subsec:mcp-primitives}

MCP servers expose capabilities to clients through three primitive types:
tools, resources, and prompts~\parencite{mcp-spec}.

\textbf{Tools} are the primary mechanism for giving an AI agent the ability
to act. Each tool has a name, a human-readable description, and a JSON Schema
that describes its input parameters. When the LLM decides that a tool is
needed to fulfil a request, it emits a structured tool call containing the
tool name and arguments. The host executes the call via the client and
returns the result to the model's context. Tools are \textit{model-initiated}
--- it is the LLM that decides when and how to invoke them.

\textbf{Resources} are URI-addressed data that the host can read and inject
into the model's context. Unlike tools, resources are \textit{host-initiated} ---
it is the host or the user that decides which resources to include, not the
model. While conceptually similar to Retrieval-Augmented Generation
(RAG)~\parencite{lewis2020rag},
where relevant documents are retrieved and injected into the prompt, MCP
resources differ in that they are explicitly declared by the server and
selected by the host or user, rather than retrieved automatically through
a similarity search.

\textbf{Prompts} are pre-defined, parameterisable message templates that
guide the model's behaviour for a specific task. A prompt can be invoked by
the user or the host and expands into one or more messages that are injected
into the conversation.

\subsection{Transport Mechanisms}
\label{subsec:mcp-transport}

MCP is transport-agnostic (the protocol defines the structure of messages
but not how they are physically carried between endpoints) and defines two
standard transport mechanisms~\parencite{mcp-spec} --- these are the transports
supported by the official SDKs~\parencite{mcp-github} and used by the
ecosystem in practice. All messages follow the
JSON-RPC~2.0 format~\parencite{jsonrpc-spec}, a lightweight remote
procedure call protocol in which each request and response is a single JSON
object identified by a method name and a unique request identifier.

\textbf{Standard I/O (stdio)} is the simplest transport. The host launches
the MCP server as a child process and communicates with it over the process's
standard input and standard output streams. Each JSON-RPC message is a
newline-delimited JSON object. This transport requires no network
configuration, has no authentication overhead, and is inherently scoped to
the local machine, making it well-suited for locally-installed tools.

\textbf{HTTP with Server-Sent Events (SSE)} is the remote transport. The
client sends requests to the server via HTTP POST, and the server delivers
responses and unsolicited notifications back via an SSE stream. This allows
MCP servers to be deployed as network services, enabling multi-user scenarios
and remote infrastructure management. A newer \textit{Streamable HTTP}
transport, which consolidates both directions into a single HTTP endpoint, is
also defined in the specification as the recommended transport for new remote
deployments~\parencite{mcp-spec}.

\section{Kubernetes and OpenShift}
\label{sec:kubernetes}

This section introduces the two platform layers that underpin RHOAI:
Kubernetes as the open-source orchestration engine
(Subsection~\ref{subsec:kubernetes-arch}), and Red Hat OpenShift as the
commercial distribution that extends it with enterprise features
(Subsection~\ref{subsec:openshift}).

\subsection{Kubernetes Architecture}
\label{subsec:kubernetes-arch}

Kubernetes is an open-source platform for automating the deployment, scaling,
and management of containerised applications~\parencite{kubernetes-docs}. It
was originally designed by Google and is now maintained by the Cloud Native
Computing Foundation (CNCF)~\parencite{cncf}. Kubernetes provides a declarative configuration
model: users describe the \emph{desired state} of their applications in YAML or
JSON manifests, and the platform's control loop continuously reconciles the
actual state of the cluster to match. This section introduces the core Kubernetes
architectural concepts that are relevant to workbench management.

\paragraph{Nodes and the control plane.}
A Kubernetes cluster consists of a \emph{control plane} and a set of worker
machines called \emph{nodes}. The control plane runs the API server, scheduler,
and controller manager, which together accept user requests, decide where
workloads should run, and ensure the desired state is maintained. Each worker
node runs a \texttt{kubelet} agent that manages the \emph{pods} (the smallest
deployable units, described below) scheduled on that node and reports status
back to the control plane~\parencite{kubernetes-docs}.

\paragraph{Pods.}
The smallest deployable unit in Kubernetes is a \emph{pod} --- a group of one
or more containers that share the same network namespace and
storage~\parencite{kubernetes-pods}. In practice, most pods contain a single
application container. Every workbench in Red Hat OpenShift AI runs
as a pod.

\paragraph{Namespaces.}
Namespaces provide a mechanism for isolating groups of resources within a single
cluster~\parencite{kubernetes-namespaces}. In the context of Red Hat OpenShift
AI, each data-science project maps to a Kubernetes namespace.

\paragraph{Persistent Volumes and Persistent Volume Claims.}
Containers are ephemeral by default: any data written inside a container is lost
when the pod is terminated. To address this limitation, Kubernetes introduces a
two-layer storage abstraction~\parencite{kubernetes-pv}. A \emph{PersistentVolume} (PV)
represents a piece of storage provisioned in the cluster. A
\emph{PersistentVolumeClaim} (PVC) is a user's request for storage; when a PVC
is created, Kubernetes binds it to a suitable PV. Workbenches mount a
PVC to persist notebooks and data across restarts.

\paragraph{StatefulSets.}
A \emph{StatefulSet} manages a set of pods with stable network identities and
persistent storage~\parencite{kubernetes-statefulsets}. Unlike a Deployment,
which treats all pods as interchangeable, a StatefulSet guarantees that each pod
retains its identity and its associated PVC across rescheduling. Workbenches are
backed by StatefulSets, which ensures that a user's notebook environment is
preserved even if the underlying node changes.

\paragraph{Custom Resource Definitions.}
Beyond these built-in resources, one of Kubernetes' most powerful extensibility
features is the ability to define \emph{Custom Resource Definitions}
(CRDs)~\parencite{kubernetes-crd}. A CRD registers a new resource type with
the Kubernetes API server, allowing users and operators to manage
domain-specific objects --- such as machine learning notebooks --- with the same
tools and workflows used for built-in resources like pods or services. The
Kubeflow project defines a \texttt{Notebook} CRD (API group
\texttt{kubeflow.org/v1}) that represents a single notebook environment.

\paragraph{Labels and annotations.}
Additionally, Kubernetes objects carry two kinds of key-value
metadata~\parencite{kubernetes-labels}. \emph{Labels} are used for selection
and filtering --- for example, RHOAI marks all notebook ImageStreams with the
label \texttt{opendatahub.io/notebook-image=true} so that they can be
distinguished from other ImageStreams in the namespace that are not notebook
images. \emph{Annotations} store
non-identifying metadata such as display names, image version hashes, or
hardware profile references. In RHOAI, workbench status, the selected notebook
image, and the hardware profile are all stored as annotations on the workbench
resource, as described in Section~\ref{sec:notebooks-workbenches}.

\subsection{Red Hat OpenShift}
\label{subsec:openshift}

Red Hat OpenShift is a commercial Kubernetes distribution developed by
Red Hat~\parencite{openshift-docs}. It packages upstream Kubernetes with a
set of additional components and wraps them in enterprise support,
certified operators, and a hardened security model. While any standard
Kubernetes cluster can run containerised workloads, OpenShift adds several
features that are particularly relevant to the platform stack discussed in this
thesis.

\paragraph{Projects.}
OpenShift introduces the concept of a \emph{project}, which is a thin wrapper
around a Kubernetes namespace that adds default role bindings, network
policies, and resource quotas~\parencite{openshift-projects}. In practice,
every OpenShift project maps one-to-one to a namespace, and the terms are often
used interchangeably.

\paragraph{ImageStreams.}
Standard Kubernetes references container images by their full registry URL.
OpenShift extends this model with
\emph{ImageStreams}~\parencite{openshift-imagestreams}, which are
namespace-scoped objects that track one or more tagged versions of a container
image. An
ImageStream decouples workloads from specific registry URLs: when a new image
version is pushed, the ImageStream is updated and can automatically trigger
redeployments. Red Hat OpenShift AI uses ImageStreams (API group
\texttt{image.openshift.io/v1}) to manage the catalogue of notebook images
available for workbenches.

\paragraph{Routes and built-in OAuth.}
OpenShift provides \emph{Routes} as a native mechanism for exposing HTTP and
HTTPS services to external traffic~\parencite{openshift-routes}, fulfilling
a role similar to Kubernetes Ingress but with tighter integration into the
platform. Each workbench is exposed through a Route, which gives it a stable
URL. OpenShift also ships a built-in OAuth server that handles user
authentication~\parencite{openshift-oauth}. Workbenches leverage this to
ensure that only authenticated users can access their JupyterLab environments.

\paragraph{Operators and the Operator Lifecycle Manager.}
OpenShift uses the \emph{Operator} pattern extensively to manage complex
software on top of the cluster~\parencite{openshift-operators}. An Operator is
a Kubernetes controller that watches custom resources and reconciles them toward
their desired state. The Operator Lifecycle Manager (OLM) handles installation,
upgrades, and dependency resolution for Operators. Red Hat OpenShift AI itself
is installed as an Operator, which in turn deploys and manages the Kubeflow
components, dashboard, and other services that make up the platform.

\section{Kubeflow, Open Data Hub, and Red Hat OpenShift AI}
\label{sec:kubeflow-odh-rhoai}

This section introduces the software layers that sit on top of OpenShift and
together provide the machine-learning platform: Kubeflow as the upstream
open-source framework (Section~\ref{subsec:kubeflow}), Open Data Hub as the
community project that integrates Kubeflow with OpenShift
(Section~\ref{subsec:odh}), Red Hat OpenShift AI as its commercial counterpart
(Section~\ref{subsec:rhoai-platform}), and hardware profiles as the mechanism
for defining compute-resource constraints
(Section~\ref{subsec:hardware-profiles}).

\subsection{Kubeflow}
\label{subsec:kubeflow}
Kubeflow is an open-source project that aims to make deployments of machine
learning workflows on Kubernetes simple, portable, and
scalable~\parencite{kubeflow-docs}. Rather than being a single monolithic
application, Kubeflow is a collection of components --- each
addressing a different stage of the ML lifecycle --- that are deployed as
Operators and custom resources on a Kubernetes cluster. Key components include
Kubeflow Pipelines for orchestrating multi-step training workflows, KServe for
model serving, Katib for hyperparameter tuning, and Kubeflow Notebooks for
interactive development environments.

The most important Kubeflow component for workbench management is
\textbf{Kubeflow Notebooks}, which provides a safe, scalable place for data scientists
to write code. The Notebook CRD, its controller, and its relationship to
RHOAI workbenches are discussed in detail in
Section~\ref{sec:notebooks-workbenches}.

\subsection{Open Data Hub}
\label{subsec:odh}

Open Data Hub (ODH) is an open-source community project that serves as a
downstream of Kubeflow, adapting its components for
OpenShift~\parencite{odh-docs}. ODH reuses Kubeflow's deployment tools and
architecture while adding OpenShift-specific integrations. It provides a
dashboard, a notebook controller, model serving, and pipeline infrastructure
--- all deployed as Operators on an OpenShift cluster. Many of the custom
resource API groups (such as \texttt{opendatahub.io}) originate from ODH.
The CRDs, labels, and annotations defined by ODH form the foundation on which
the commercial platform described in the next subsection is built.

\subsection{Red Hat OpenShift AI}
\label{subsec:rhoai-platform}

Red Hat OpenShift AI (RHOAI) is Red Hat's commercial machine-learning platform
derived from Open Data Hub and built on top of
OpenShift~\parencite{rhoai-docs}. It packages the same core components as ODH
but adds enterprise hardening, certified Operators, and commercial support.
RHOAI is installed on an OpenShift cluster as an Operator and provides a
web-based \emph{dashboard} --- a graphical interface from which users can
create data-science projects, launch and manage workbenches, configure notebook
images and hardware profiles, and monitor resource consumption without writing
any YAML or using the command line.

\subsection{Hardware Profiles}
\label{subsec:hardware-profiles}

A \emph{hardware profile} is an RHOAI-specific custom resource 
that defines a named set of
compute-resource constraints for a workbench. Each profile specifies one or
more resource identifiers --- typically CPU, memory, and optionally a GPU
(referred to as an \emph{accelerator} in RHOAI) --- with
a default, minimum, and maximum count for each. When a user creates a
workbench, they select a hardware profile. Platform then translates the
profile's resource definitions into Kubernetes resource requests and limits on
the workbench's pod. Administrators can create hardware profiles to standardise
the compute tiers available to data scientists (for example, \enquote{Small} with 2
CPUs and 4\,GiB of memory, or \enquote{GPU Large} with 8 CPUs, 32\,GiB, and one
NVIDIA GPU).

\section{Kubeflow Notebooks and Workbenches}
\label{sec:notebooks-workbenches}

This section describes the topmost layer of the platform stack: the interactive
development environments that data scientists use daily. The upstream Kubeflow
project calls them \emph{Notebooks}; Red Hat OpenShift AI calls them
\emph{workbenches}. Under the hood they are the same Kubernetes resource, but
RHOAI adds additional metadata and dashboard integration.

\subsection{The Kubeflow Notebook CRD}
\label{subsec:notebook-crd}

The Kubeflow Notebook Controller defines a Custom Resource Definition called
\texttt{Notebook} in the API group
\texttt{kubeflow.org/v1}~\parencite{kubeflow-notebook-crd}. A \texttt{Notebook}
resource is structurally similar to a Kubernetes \texttt{StatefulSet}: it
contains a pod template that specifies the container image, resource requests
and limits, volume mounts, and environment variables. When a \texttt{Notebook}
resource is created, the Notebook Controller creates the corresponding
StatefulSet, which then creates a pod running the specified container image
--- typically a JupyterLab server.

The Notebook Controller also handles lifecycle operations. Setting the
annotation \texttt{kubeflow-resource-stopped} to a timestamp causes the
controller to scale the StatefulSet to zero replicas, effectively stopping the
notebook without deleting it. Removing the annotation restarts it. This
mechanism is how the RHOAI dashboard starts and stops workbenches.

\subsection{RHOAI Workbenches}
\label{subsec:rhoai-workbenches}

In Red Hat OpenShift AI, a \emph{workbench} is a Kubeflow \texttt{Notebook}
resource enriched with additional annotations and integrated into the RHOAI
dashboard~\parencite{rhoai-workbenches}. The RHOAI dashboard is the primary
way users interact with workbenches today. When a user creates a workbench
through the dashboard, it constructs a \texttt{Notebook} manifest with
RHOAI-specific annotations such as:

\begin{compactitem}
  \item \texttt{opendatahub.io/\allowbreak image-display-name} --- the human-readable name
        of the selected notebook image,
  \item \texttt{opendatahub.io/\allowbreak hardware-profile-name} --- the hardware profile
        governing CPU, memory, and GPU limits,
  \item \texttt{opendatahub.io/\allowbreak username} --- the owner of the workbench,
  \item \texttt{notebooks.opendatahub.io/\allowbreak last-image-selection} --- a reference
        to the selected ImageStream tag for upgrade tracking.
\end{compactitem}

The dashboard then submits this manifest to the Kubernetes API, where the
Notebook Controller picks it up and creates the running environment. Each
workbench is backed by a PersistentVolumeClaim that stores the user's data, 
and is exposed to the user via an OpenShift Route with OAuth
authentication.

\subsection{Notebook Images}
\label{subsec:notebook-images}

RHOAI ships a set of notebook images, each used for a specific
workflow. Examples include images with pre-installed data-science libraries
(NumPy, pandas, scikit-learn), PyTorch or TensorFlow for deep learning, and
minimal images for lightweight experimentation and testing. Each image is 
represented as an OpenShift ImageStream (see Section~\ref{subsec:openshift}) 
with one or more version tags. 
Custom images --- for example, an image with a development version of a library
not yet available in the default catalogue --- can be registered through the
RHOAI dashboard or by creating an ImageStream directly.

\subsection{The Current Management Workflow}
\label{subsec:current-workflow}

Today, managing workbenches requires either navigating the RHOAI web dashboard
or directly manipulating Kubernetes resources through \texttt{oc} or
\texttt{kubectl}. Both approaches have limitations. The dashboard is
user-friendly but manual: creating, stopping, or reconfiguring multiple
workbenches is time-consuming. The
command-line approach is scriptable but requires deep knowledge of the
underlying CRDs, annotations, and resource relationships described in this
chapter.

\chapter{Analysis and Design}
\label{chap:analysis}

The previous chapters introduced the Model Context Protocol as a standardised
way of connecting AI agents to external tools
(Chapter~\ref{chap:ai-mcp}) and described Red Hat OpenShift AI workbenches
together with the Kubernetes resources that underlie them
(Chapter~\ref{chap:rhoai}). This chapter bridges the gap between that
background knowledge and the implementation itself. It begins by stating the
motivation for the project and the concrete goals it aims to achieve, then
derives a set of functional and non-functional requirements, justifies the
key technology choices, and presents the architecture of the server.

\section{Motivation and Goals}
\label{sec:motivation}

The introduction outlined the core problem: workbench management in RHOAI
is either manual (dashboard) or requires deep Kubernetes expertise
(command line). Section~\ref{subsec:current-workflow} described these
workflows in detail. This thesis proposes an MCP-based solution that lets
users interact with the cluster through natural language, delegating the
underlying complexity to an AI agent.

As a concrete example, a data scientist could request: \enquote{create three
workbenches with an image containing PyTorch and pandas, each having 4 CPUs
and 16\,GiB of memory.} The agent interprets this request, selects the
appropriate MCP tool, constructs the parameters from the Kubeflow Notebook
CRD and RHOAI annotations (Section~\ref{subsec:rhoai-workbenches}), and
executes the operation --- all without the user needing to know how
workbenches are represented in Kubernetes.

It is worth noting that the current implementation targets the existing
Kubeflow-based workbench architecture described in
Chapter~\ref{chap:rhoai} and is intended as a proof of concept.
Notebooks~2.0~\parencite{notebooks-v2}, a redesigned notebook subsystem, is
expected to be released and integrated into RHOAI later this year. The
implications of this transition and the changes it will require in the MCP
server are discussed in Section~\ref{sec:future-work}.

With this motivation in mind, the thesis pursues the following goals:

\begin{enumerate}
  \item \textbf{Full workbench lifecycle coverage.} Provide MCP tools for
        the complete set of workbench management operations: listing,
        creating, updating, and deleting workbenches, notebook images,
        hardware profiles, persistent volume claims, and namespaces.

  \item \textbf{Resource consumption monitoring.} Provide tools to query
        resource consumption (CPU, memory, disk, and GPU) at multiple
        granularities --- per workbench, per namespace, per user, and per
        cluster --- giving administrators and data scientists visibility
        into how compute resources are being used.

  \item \textbf{Safety by default.} Operate in a read-only mode by default,
        exposing only listing and querying tools. Write operations ---
        creation, modification, and deletion --- are hidden behind an explicit
        enablement so that users can explore the server's capabilities
        without risk of accidental modifications to the cluster.

  \item \textbf{Quality assurance.} Validate correctness through unit tests
        and automated evaluation of end-to-end agent behaviour, measuring
        tool selection accuracy and parameter extraction correctness. This
        also serves the proof-of-concept purpose by establishing a methodology
        for evaluating MCP server implementations.

  \item \textbf{Exploration of all MCP primitives.} Since the
        implementation serves as a proof of concept, exercise the full
        breadth of the MCP standard --- not only tools, but also resources
        and prompts. Specifically, expose MCP resources (an image catalogue,
        available hardware profiles, and cluster namespaces) and an MCP prompt
        that orchestrates a guided workbench creation workflow, demonstrating
        how the three server primitives can work together in practice.
\end{enumerate}

\section{Requirements}
\label{sec:requirements}

This section translates the goals from Section~\ref{sec:motivation} into
concrete requirements. Functional requirements describe \emph{what} the
system must do; non-functional requirements describe \emph{how} it must
behave.

\subsection{Functional Requirements}
\label{subsec:functional-req}

\begin{enumerate}
  \item \textbf{FR-1: Workbench management.} The server must provide tools to
        list, create, update, and delete workbenches. Listing must support
        both a single-namespace and a cross-namespace mode. Each workbench
        entry must include the workbench name, notebook image, hardware profile, and attached
        persistent volume claim.

  \item \textbf{FR-2: Workbench lifecycle control.} The server must provide
        a tool to start and stop a workbench without deleting it, using the
        \texttt{kubeflow-resource-stopped} annotation mechanism described in
        Section~\ref{subsec:notebook-crd}.

  \item \textbf{FR-3: Notebook image management.} The server must provide
        tools to list all available notebook images (including version tags,
        Python dependencies, and bundled software), create custom images by
        registering new ImageStreams, update existing images, and delete them.

  \item \textbf{FR-4: Hardware profile management.} The server must provide
        tools to list, create, update, and delete hardware profiles, each
        specifying resource identifiers (CPU, memory, and optionally GPU)
        with default, minimum, and maximum values.

  \item \textbf{FR-5: Storage management.} The server must provide tools to
        list, create, resize, and delete persistent volume claims (PVCs).
        Resizing supports expansion only, as Kubernetes does not support
        shrinking.

  \item \textbf{FR-6: Namespace and pod listing.} The server must provide
        tools to list all namespaces in the cluster and to list pods in a
        given namespace.

  \item \textbf{FR-7: Resource consumption monitoring.} The server must
        provide tools to query resource consumption (CPU, memory, disk, and
        GPU) at four granularities: per workbench, per namespace, per user,
        and per cluster.

  \item \textbf{FR-8: MCP resources.} The server must expose at least one
        MCP resource to demonstrate the resource primitive and its usage in
        a real-world scenario.

  \item \textbf{FR-9: MCP prompt.} The server must expose at least one MCP
        prompt to demonstrate the prompt primitive and its usage in a
        real-world scenario.
\end{enumerate}

\subsection{Non-Functional Requirements}
\label{subsec:nonfunctional-req}

\begin{enumerate}
  \item \textbf{NFR-1: Safety.} The server must start in read-only mode by
        default. Write operations (create, update, delete) must only be
        registered when explicitly enabled via the \texttt{-mode write}
        command-line flag or the \texttt{MCP\_RHOAI\_\allowbreak MODE=write}
        environment variable.

  \item \textbf{NFR-2: Host independence.} The server must communicate
        exclusively through the MCP standard and must not contain any
        host-specific code. It must be usable from any MCP-compatible host.

  \item \textbf{NFR-3: Local cluster authentication.} The server does not
        manage its own authentication. The user must be logged in to an
        OpenShift cluster locally (via \texttt{oc login}) before starting
        the server. All Kubernetes API calls are executed using the
        credentials stored in the user's \texttt{kubeconfig} file, and
        therefore run with the permissions of the logged-in user.

  \item \textbf{NFR-4: Code quality.} The codebase must pass static
        analysis and linting checks, and follow clear package separation.

  \item \textbf{NFR-5: Unit testing.} All tools must have unit tests
        covering both success and error paths.

  \item \textbf{NFR-6: Evaluation.} End-to-end agent behaviour must be
        evaluated using an automated framework that measures tool
        selection accuracy, parameter extraction correctness, and execution
        success rate.
\end{enumerate}

\section{Technology Choices}
\label{sec:technologies}

This section justifies and describes the key technology used for the
implementation.

\paragraph{Go.}
The server is written in Go~\parencite{go-lang}. Go was chosen for two
reasons. First, it is the dominant language in the Kubernetes ecosystem ---
Kubernetes itself, OpenShift, and the Kubeflow Notebook Controller are all
written in Go, and the official Kubernetes client library
(\texttt{client-go}) is a Go module. Using Go means the server can import
\texttt{client-go} directly without a foreign-function interface or an
HTTP wrapper. A Python or TypeScript implementation would need to
communicate with the cluster through a generated REST client or a wrapper
library rather than using the same native client that Kubernetes itself
uses. Second, Go compiles to a single static binary with no runtime
dependencies, which simplifies distribution --- users only need to place
the binary on their \texttt{PATH} and point their MCP host configuration at
it. By contrast, a Python-based server would require the user to have a
compatible Python interpreter and manage a virtual environment with the
correct dependencies installed.

\paragraph{MCP Go SDK.}
Given the choice of Go as the implementation language, the server uses the
official MCP Go SDK~\parencite{mcp-go-sdk} (version 1.1.0) for all
protocol-level concerns. The alternative would be implementing the MCP
protocol from scratch, which would require manually handling JSON-RPC
message parsing, capability negotiation, and JSON Schema generation for
tool inputs --- a significant effort that would duplicate work already done
in the official SDK. Using the official SDK also ensures protocol compliance as the
specification evolves. The SDK handles creating the MCP server instance,
registering tools with their JSON Schema input definitions (derived
automatically from Go struct tags), registering resources and prompts, and
running the transport loop. Its typed tool registration function
(\texttt{mcp.AddTool}) accepts a Go struct as the input type and
automatically generates the JSON Schema that is advertised to the host,
eliminating manual schema maintenance and reducing the risk of
inconsistencies between the declared schema and the actual implementation.

\paragraph{golangci-lint.}
Static analysis is performed by
\texttt{golangci-lint}~\parencite{golangci-lint}, a tool that runs multiple
Go linters and aggregates their results into a single invocation. The alternative
would be running each linter separately (\texttt{go vet}, \texttt{errcheck},
\texttt{staticcheck}, etc.), which complicates build configuration and
slows down the feedback loop. \texttt{golangci-lint} is the de facto
standard in the Go ecosystem: it runs linters in parallel for speed,
provides a unified configuration format, and is widely adopted by
open-source Go projects. It is integrated into the build process through
the Makefile: \texttt{make build} runs \texttt{golangci-lint run} before
compiling the binary, ensuring that code quality checks pass on every build.

\paragraph{stdio transport.}
The server uses the stdio transport
(Section~\ref{subsec:mcp-transport}) exclusively, initialised in the entry
point as:

\begin{lstlisting}[language=Go]
server.Run(context.Background(), &mcp.StdioTransport{})
\end{lstlisting}

This choice reflects the intended deployment model: the MCP server runs as
a local process on the same machine as the AI host, typically the
developer's workstation. Although the server communicates with a remote
Kubernetes cluster (via the user's \texttt{kubeconfig} credentials), the
MCP protocol itself operates locally between the host application and the
server. An HTTP/SSE transport would make sense if the MCP server were
deployed as a shared network service accessed by multiple users, but this
would introduce additional complexity --- TLS certificates, authentication
tokens, and service deployment --- without clear benefit for the
single-user, proof-of-concept scope of this implementation. The stdio
transport requires no network configuration, is inherently secure (no
exposed ports), and integrates seamlessly with how MCP hosts such as Cursor
and Claude Desktop manage local tool servers. If multi-user or remote deployment is needed in the future, switching to
the HTTP/SSE or Streamable HTTP transport would be straightforward at the
code level (only the transport initialisation changes), but would also
require setting up TLS certificates, an authentication layer, and deploying
the server as a network service.

\paragraph{Promptfoo.}
End-to-end evaluation uses the Promptfoo
framework~\parencite{promptfoo}, an open-source tool for testing LLM
applications. Alternatives such as DeepEval~\parencite{deepeval} were
considered --- DeepEval offers over fifty evaluation metrics, including a
dedicated tool-correctness metric, but that breadth introduces complexity
that is unnecessary when the only goal is to evaluate tool-calling
behaviour.
Promptfoo is more focused: its entire configuration fits into a single
YAML file, it requires no custom evaluation code, and it directly supports
the workflow needed here --- sending natural-language prompts to an LLM,
capturing the tool calls the model emits, and checking them against
expected outcomes. It measures tool selection accuracy and parameter
extraction correctness. It also supports multiple LLM providers (OpenAI,
Anthropic, Google), making it straightforward to compare tool-calling
quality across models.


\section{Architecture}
\label{sec:architecture}

This section describes the internal structure of the MCP server: how the
codebase is organised, how the two operation modes are implemented, how the
server communicates with the OpenShift cluster, and how the project is
built.

\subsection{Project Structure}
\label{subsec:project-structure}

The project root contains the following key files:

\begin{compactitem}
  \item \texttt{main.go} --- the entry point that creates the MCP server
        instance, registers tools, resources, and prompts, and starts the
        stdio transport loop.
  \item \texttt{Makefile} --- drives the build pipeline described in
        Section~\ref{subsec:build-pipeline}.
  \item \texttt{.golangci.yml} --- configuration for the golangci-lint
        static analysis tool.
  \item \texttt{promptfoo.yaml} --- defines the evaluation test suite used
        to measure tool selection accuracy
        (Section~\ref{sec:evaluation}).
  \item \texttt{.github/workflows/ci.yml} --- GitHub Actions workflow that
        runs linting and unit tests on every push and pull request,
        ensuring continuous integration.
\end{compactitem}

The source code is organised into four packages:

\begin{compactitem}
  \item \texttt{core} --- shared type definitions (input/output structs for
        every tool), Kubernetes GroupVersionResource constants, and cluster
        authentication helpers.
  \item \texttt{tools} --- the implementation of every MCP tool, plus a
        registry module that registers tools with the MCP server. The
        registry exposes two functions:
        \texttt{RegisterReadOnlyTools}, which registers the listing and
        monitoring tools that are always available, and
        \texttt{RegisterWriteTools}, which additionally registers the
        create, update, and delete tools. The entry point inspects the
        \texttt{MCP\_RHOAI\_MODE} environment variable and calls one or both
        functions accordingly.
  \item \texttt{resources} --- the implementations of the three MCP
        resources: the Image Catalog, Hardware Profiles, and Namespaces.
        A registry module registers all resources with the MCP server.
  \item \texttt{prompts} --- the implementation of the Create Workbench
        MCP prompt, together with a registry module that registers it with
        the MCP server.
\end{compactitem}

\subsection{Two-Mode Design}
\label{subsec:two-mode}

The server's safety model is implemented at the registration level rather
than at the execution level. When the server starts, it determines the
operation mode from two sources: the \texttt{MCP\_RHOAI\_MODE} environment
variable and the \texttt{-mode} command-line flag. The flag, if provided,
takes precedence over the environment variable, allowing users to override
the mode without modifying their shell environment. If the resolved mode is
\texttt{write}, the server calls \texttt{RegisterWriteTools} followed by
\texttt{RegisterReadOnlyTools}, making all tools available. For any other
value (or when neither the flag nor the variable is set), only
\texttt{RegisterReadOnlyTools} is called. Because tools that are not
registered are never advertised to the host during capability negotiation,
the LLM cannot invoke them --- it does not know they exist. This approach is
simpler and more robust than runtime permission checks, since there is no
code path that could accidentally bypass a guard.

\subsection{Kubernetes Client Strategy}
\label{subsec:client-strategy}

The server uses two types of Kubernetes clients from the
\texttt{client-go} library~\parencite{client-go}. The \textbf{typed client}
(\texttt{kubernetes.Clientset}) is used for operations on built-in
resources such as pods and namespaces, where the Go type system provides
compile-time safety. The \textbf{dynamic client}
(\texttt{dynamic.DynamicClient}) is used for custom resources --- Kubeflow
Notebooks, OpenShift ImageStreams, and hardware profiles --- where no
generated Go types are available and the server must work with
\texttt{unstructured.Unstructured} objects. Both clients are constructed from
the user's \texttt{kubeconfig} file, reusing whatever credentials and
permissions the user has when they run \texttt{oc login}.

To support unit testing, both clients are exposed as package-level function
variables (\texttt{GetClientSet} and \texttt{GetDynamicClient}) that can be
replaced with mock implementations in test code, satisfying NFR-5.

\subsection{Build Pipeline}
\label{subsec:build-pipeline}

The project uses a Makefile to integrate all quality checks into a single
build command. Running \texttt{make build} executes three stages in
sequence: first \texttt{golangci-lint run} to verify that the code passes
all configured linters, then \texttt{go test} to run the unit test suite,
and finally \texttt{go build} to compile the binary. If any stage fails,
the build stops immediately. This ensures that every produced binary has
passed both linting and tests. Evaluation is run separately via
\texttt{make eval}, which invokes Promptfoo against the compiled server.

The previous chapter defined the requirements, technology choices, and

\section{MCP Tools}
\label{sec:tools}

The server exposes 20 MCP tools covering five resource domains. Each
subsection below opens with a table listing its tools and then discusses
the design decisions and non-trivial implementation details. In all
tables, tools marked \textit{(write)} are only registered when the
environment variable \texttt{MCP\_RHOAI\_MODE=write} is set; all other
tools are always available. Notably, several listing operations that
require no parameters (such as listing images, hardware profiles, and
namespaces) are exposed as MCP resources rather than tools, providing a
cleaner interface for clients (Section~\ref{sec:resources-prompts}).

Each tool is registered with the MCP server using the SDK's
\texttt{mcp.AddTool} function, which accepts a \texttt{mcp.Tool}
descriptor (name and description) and a Go function that implements the
tool's logic. Every tool function follows the
same high-level pattern: obtain a Kubernetes client, perform the required
API call, transform the result into a typed output struct, and return it.
Errors are propagated back to the host as standard MCP error responses.

Table~\ref{tab:tools-workbench} lists the five workbench management tools.
Workbench management is the most complex part of the server, comprising
tools that operate on Kubeflow
\texttt{Notebook} resources (API group \texttt{kubeflow.org/v1}) through
the dynamic Kubernetes client.

\paragraph{Listing.}
The \texttt{list\_workbenches} tool is the foundation on which several
other tools are built. For each \texttt{Notebook} resource in the specified
namespace, the tool reads RHOAI-specific annotations to extract the
image display name, image tag, hardware profile
name, and owner. Running status is determined by the presence of the
\texttt{kubeflow-resource-\allowbreak stopped} annotation: if set, the workbench is
stopped; otherwise, it is running. For running workbenches, it
additionally queries the typed client for pods labelled
\texttt{notebook-name=\allowbreak <workbenchName>} to obtain uptime from the pod's
start time. Disk usage is read from the PVC's requested storage capacity.
The result is a list of \texttt{WorkbenchInfo} structs containing the
workbench name, user, status, image, hardware profile, PVC name, namespace,
uptime, and resource consumption (CPU, memory, disk, GPU). When the
namespace parameter is empty or not provided, the tool uses an empty
namespace string in the Kubernetes API call, which returns results across all
namespaces, giving administrators a cluster-wide view.

\paragraph{Creation.}
The \texttt{create\_workbench} tool is the most complex in the server.
It
must resolve the user-specified image display name and tag to a concrete
container image URL by looking up the corresponding ImageStream, optionally
create a PVC (defaulting to the workbench name and 10\,GiB if none is
provided), and fall back to the default hardware profile
(Section~\ref{sec:resources-prompts}) when no profile is specified. The
manifest is constructed as an \texttt{unstructured.\allowbreak Unstructured} object
with the same annotations the RHOAI dashboard would set ---
\texttt{opendatahub.io/\allowbreak image-display-name} and
\texttt{notebooks.opendatahub.io/\allowbreak last-image-selection},
among others. The
container spec includes JupyterLab server arguments, two volume mounts
(the user's PVC and a shared-memory \texttt{emptyDir}), and resource
requests and limits derived from the hardware profile. After submission,
the Notebook Controller creates the running environment. This design
ensures that workbenches created through the MCP server are
indistinguishable from those created through the dashboard.

\paragraph{Updates and lifecycle control.}
The \texttt{update\_workbench} tool supports three independent update
dimensions --- the notebook image, the hardware profile, and the attached
PVC --- each applied only when the corresponding input fields are
non-empty, allowing partial updates. The
\texttt{change\_workbench\_status} tool starts or stops a workbench by
manipulating the \texttt{kubeflow-resource-stopped} annotation: setting it
to the current timestamp stops the workbench; removing it (via a
\texttt{nil} merge patch) restarts it. Before making any change, the
tool checks the current state and returns early if the workbench is
already in the requested state, avoiding redundant Kubernetes API calls.
The \texttt{delete\_workbench} tool issues a single \texttt{Delete} call;
the Notebook Controller handles cleanup of the associated StatefulSet and
pod, but the PVC is intentionally preserved so that the user's data is
not lost.

\section{MCP Resources and Prompts}
\label{sec:resources-prompts}

Beyond tools, the server exposes three MCP resources and one MCP prompt.
Together with the tools described above, these demonstrate all three
MCP server primitives in a real-world scenario. Notably, listing operations
that require no parameters --- images, hardware profiles, and namespaces ---
are exposed as resources rather than tools. This design follows the MCP
specification's guidance that resources are appropriate for data that the
client can read without needing to provide input parameters.

\subsection{Image Catalog Resource}
\label{subsec:image-catalog}

\begin{sloppypar}
The Image Catalog is registered with the URI
\texttt{resource://mcp-server-rhoai/\allowbreak images} and the MIME type
\texttt{application/json}. When read, it calls the
\texttt{GetImages} function, which queries all ImageStreams in the default
RHOAI namespace that carry the \texttt{opendatahub.io/\allowbreak notebook-image=true}
label. For each image, it extracts the display name from annotations, the
container image URL from the ImageStream's \texttt{status.docker\-Image\-Repository}
field, and all version tags with their Python dependency and software
annotations. The result is serialised as a JSON array and returned to the
host. An agent can read this resource before creating a workbench to
discover which images are available and select a suitable one.
\end{sloppypar}

\subsection{Hardware Profiles Resource}
\label{subsec:hw-profiles-resource}

\begin{sloppypar}
The Hardware Profiles resource is registered with the URI
\texttt{resource://mcp-server-rhoai/\allowbreak hardware-profiles} and the MIME type
\texttt{application/json}. When read, it queries all HardwareProfile custom
resources in the RHOAI namespace and returns each profile's resource
identifiers with their default, minimum, and maximum values. This resource
replaces what was previously a listing tool, providing a cleaner interface
for clients that simply need to discover available profiles before creating
or updating a workbench.
\end{sloppypar}

\subsection{Namespaces Resource}
\label{subsec:namespaces-resource}

\begin{sloppypar}
The Namespaces resource is registered with the URI
\texttt{resource://mcp-server-rhoai/\allowbreak namespaces} and the MIME type
\texttt{application/json}. When read, it queries the Kubernetes API for all
namespaces in the cluster and returns them as a JSON array of namespace names.
This allows an agent to discover available namespaces before performing
operations that require a namespace parameter, such as creating workbenches
or listing PVCs.
\end{sloppypar}

\subsection{Create Workbench Prompt}
\label{subsec:create-wb-prompt}

The Create Workbench prompt is registered under the name
\texttt{create-workbench-\allowbreak prompt} with two required arguments:
\texttt{namespace} and \texttt{name}. When invoked, it returns
a single user-role message that instructs the agent to consult the Image
Catalog resource to find a suitable Data Science image (preferring
Python~3.12) and then call the \texttt{create\_workbench} tool. This
prompt demonstrates how the three MCP primitives interact in practice: a
prompt guides the agent to first read a resource (the Image Catalog) and
then invoke a tool (Create Workbench), orchestrating a multi-step workflow
through a single user action.

\section{Security}
\label{sec:security}

Security is addressed at two levels: the two-mode design described in
Section~\ref{subsec:two-mode}, which prevents accidental cluster
modifications, and the Kubernetes authentication model.

The server does not implement its own authentication or authorisation.
Instead, it relies entirely on the user's existing OpenShift credentials.
Both the typed and dynamic Kubernetes clients are constructed from the
\texttt{kubeconfig} file at \texttt{\textasciitilde/.kube/config}, which
stores the token obtained via \texttt{oc login}. Every API call the server
makes therefore runs with the permissions of the logged-in user; if the user
does not have permission to, for example, delete workbenches in a certain
namespace, the Kubernetes API server rejects the request and the error is
propagated back to the agent.

This delegation model has two advantages. First, it avoids introducing a
separate credential management system --- the server reuses the same
authentication flow that platform engineers already use. Second, it ensures
that the server cannot escalate privileges beyond what the user already has,
since every API call is subject to the same permission checks that the
cluster enforces for all users.

The image deletion tool includes additional application-level safety checks. It
refuses to delete images that are marked as RHOAI defaults (by inspecting
the \texttt{internal.config.kubernetes.io/\allowbreak previousNamespaces} annotation)
and images that are currently in use by any workbench (by scanning all
workbenches across namespaces). These checks prevent accidental removal of
images that would break existing workbenches.

A broader risk that affects any system connecting an LLM to external data
is \textit{prompt injection}~\parencite{greshake2023indirect}. In this
attack, malicious instructions are embedded in data that the LLM
processes --- for example, in a database field, a document, or MCP tool
metadata --- causing the model to execute unintended actions. Because
the server source code is released under an open-source license, users
can audit the tool definitions and verify that no malicious prompts are
embedded in the server itself. However, the server cannot prevent
prompt injection originating from cluster data it retrieves: when
listing workbenches or namespaces, it returns names and descriptions
stored in the cluster, and an attacker with cluster access could inject
malicious text into these fields. Standard Kubernetes access controls
therefore remain essential, and high-security environments may consider
deploying an MCP gateway that inspects and sanitises traffic between
the client and server at runtime.

\section{Code Quality}
\label{sec:code-quality}

Code quality is maintained through static analysis and unit testing, both
integrated into the build pipeline.

\subsection{Static Analysis}
\label{subsec:static-analysis}

The project uses \texttt{golangci-lint} with five enabled linters:
\texttt{errcheck} (ensures error return values are checked),
\texttt{govet} (reports suspicious constructs),
\texttt{ineffassign} (detects ineffectual assignments),
\texttt{staticcheck} (a suite of advanced static analysis checks), and
\texttt{unused} (finds unused code). Every build runs
\texttt{golangci-lint run} as the first stage; if any linter reports an
issue, the build fails immediately.

\subsection{Unit Testing}
\label{subsec:unit-testing}

Unit tests validate tool behaviour against a simulated OpenShift cluster
without requiring access to a live environment. This is made possible by
the injectable client design described in
Section~\ref{subsec:client-strategy}: the \texttt{GetClientSet} and
\texttt{GetDynamicClient} function variables in the \texttt{tools} package
are replaced with fake implementations in test code. The common setup
logic is centralised in a shared \texttt{test\_helpers\_test.go} file that exposes
\texttt{setupFakeClient} and \texttt{setupFakeClientSet} helpers; each
helper injects a \texttt{client-go} fake into the package-level variable
and restores the original on cleanup. Some tools that depend on other
tools internally (for example, the resource consumption tools call the
workbench listing logic) use additional function-level mocks such as
\texttt{listWorkbenchesFn} that are replaced in tests with simple
functions returning predefined data.
The test suite comprises eight test files covering every tool domain:

\begin{compactitem}
  \item \textbf{Workbenches} --- tests for listing (stopped and running
        workbenches), creation (including automatic PVC creation), updates,
        deletion, and status changes. Pure helper
        functions such as image tag parsing and resource requirement
        construction are tested separately.
  \item \textbf{Hardware profiles} --- listing, creation, update, deletion,
        and parsing of profile resource identifiers.
  \item \textbf{Notebook images} --- creation, update, and deletion of
        custom images, including verification that default images and
        images in use by workbenches cannot be deleted. The
        \texttt{ListImages} tool and the underlying \texttt{GetImages}
        function (which backs the Image Catalog resource) are tested with
        fake ImageStream objects.
  \item \textbf{Storage} --- PVC creation, deletion, resize (verifying
        that shrinking is rejected), and listing.
  \item \textbf{Namespaces and pods} --- listing with typed client fakes.
  \item \textbf{Resource consumption} --- the aggregation helpers
        (\texttt{parse\-Resource\-Value}, \texttt{sum\-Resource\-Values}) are
        tested directly, and all four granularity tools are tested
        with predefined workbench data.
\end{compactitem} 

\section{Evaluation}
\label{sec:evaluation}

Unit tests verify that each tool behaves correctly in isolation, but they
cannot answer the question that matters most: will an AI agent actually use
these tools successfully? The value of an MCP server depends entirely on
whether language models can interpret natural-language requests, select
appropriate tools, and extract correct parameters from conversational input.
This makes end-to-end evaluation essential.

Evaluating LLM-based systems presents a fundamental challenge: language models
are inherently non-deterministic. The same prompt may produce different tool
calls across runs due to sampling randomness, and minor prompt variations can
lead to entirely different tool selections. A robust evaluation must therefore
test a representative set of scenarios and accept that perfect reproducibility
is not achievable. The goal is to verify that the model \emph{generally}
selects the right tools and extracts the right parameters, not that it does so
identically every time.

End-to-end evaluation uses the Promptfoo framework~\parencite{promptfoo} to
measure how well an LLM agent uses the MCP server's tools in response to
natural-language requests. Promptfoo was chosen for its simplicity --- the
entire evaluation is configured in a single YAML file (\texttt{promptfoo.yaml})
with no custom evaluation code required, and it can be run with
\texttt{make eval}.

\subsection{Evaluation Setup}
\label{subsec:eval-setup}

Promptfoo connects to the compiled MCP server binary as an MCP provider,
starting the server with the \texttt{-mode write} flag so that all tools
are available. The active provider in the configuration is Google's
Gemini~2.5~Pro.

Each test case consists of a natural-language prompt (the \texttt{prompt}
variable) and one or more assertions. The assertions use Promptfoo's
\texttt{tool-call-f1} metric, which checks whether the set of tools the
model actually called matches the expected set. This metric captures both
\emph{precision} (the model did not call unnecessary tools) and
\emph{recall} (the model called all required tools), combining them into
a single F1 score.

\subsection{Test Cases}
\label{subsec:eval-cases}

The evaluation suite includes 22~test cases organised into seven categories,
providing comprehensive coverage of all tool domains:

\begin{compactitem}
  \item \textbf{Workbench listing} (2~tests) --- listing workbenches
        cluster-wide and within a specific namespace, verifying that the model
        selects the appropriate tool variant and extracts namespace parameters.
  \item \textbf{Workbench CRUD} (5~tests) --- creating, updating, and
        deleting workbenches, plus starting and stopping them via the status
        change tool.
  \item \textbf{Pods} (1~test) --- listing pods within a specific namespace.
  \item \textbf{Notebook images} (3~tests) --- creating custom images with
        name and location, updating image metadata, and deleting images.
  \item \textbf{Hardware profiles} (3~tests) --- creating, updating, and
        deleting hardware profiles with resource specifications.
  \item \textbf{Storage} (3~tests) --- listing PVCs in a namespace,
        creating a PVC with a specified size, and resizing an existing PVC.
  \item \textbf{Resource consumption} (5~tests) --- querying consumption
        at all four granularities (per-workbench, per-namespace, per-user,
        and cluster-wide), with multiple prompt variations to test robustness.
\end{compactitem}

Promptfoo evaluates only tool-calling behaviour; it does not support testing
MCP resources or prompts. Consequently, the listing operations that are exposed
as resources (available notebook images, hardware profiles, and namespaces) are
not covered by this automated evaluation. Their correctness is verified through
manual testing and unit tests instead.

Each test case verifies both tool selection (via the \texttt{tool-call-f1}
metric) and parameter extraction (via \texttt{contains} assertions that
check for expected argument values in the tool call). A~2-second delay is
configured between test cases to avoid API rate limiting.

\subsection{Running the Evaluation}
\label{subsec:eval-running}

\begin{sloppypar}
The evaluation requires an API key for the configured LLM provider. The
default configuration uses Google Gemini, so users must set the
\texttt{GOOGLE\_API\_KEY} environment variable before running. The
evaluation is then invoked via \texttt{make eval}, which runs
\texttt{npx promptfoo@latest eval -c promptfoo.yaml}. Results are written
to \texttt{promptfoo-results.json} and can also be explored in a web-based
dashboard via \texttt{make eval-view}. The YAML-based configuration makes
it straightforward to add new test cases, switch providers, or adjust
assertion types as the tool set evolves.
\end{sloppypar}

\subsection{Results and Learnings}
\label{subsec:eval-results}

The evaluation was run using Google Gemini~2.5~Pro as the LLM provider. The
evaluation was executed multiple times to verify consistency, and every run
achieved a 100\% pass rate: all 22~test cases passed, with 52~individual
assertions verified successfully. This consistent result across repeated runs
demonstrates that the tool names, descriptions, and parameter schemas are
sufficiently clear for a state-of-the-art language model to reliably select
the correct tool and extract the required parameters from natural-language
requests.

Running the evaluation iteratively during development proved valuable for
improving tool descriptions. Early runs revealed cases where the model
selected incorrect tools or failed to extract parameters, which pointed to
ambiguities in the tool definitions. Several refinements emerged from this
process:

\begin{compactitem}
  \item Optional fields must be explicitly marked with \texttt{omitempty} in
        the Go struct tags, and the JSON schema descriptions should state the
        default value that will be used when the field is omitted.
  \item Enumerated values should be listed explicitly in the description ---
        for example, the \texttt{change\_workbench\_status} tool describes its
        status parameter as \enquote{0 for running, 1 for stopped} rather than
        relying on the model to infer the mapping.
  \item Testing with different models (Gemini~2.5~Pro, Gemini~2.5~Flash,
        Claude~3.5~Sonnet) exposed robustness issues: simpler models are
        stricter about parameter formats, making them useful for catching
        under-specified descriptions that more capable models might tolerate.
\end{compactitem}

These learnings apply broadly to MCP server development: the evaluation
framework not only validates correctness but also serves as a feedback loop
for improving tool usability across different language models.

\chapter{Conclusion}
\label{chap:conclusion}

This thesis presented the design and implementation of an MCP server for
Red Hat OpenShift AI workbenches. The server is written in Go using the
official MCP Go SDK and communicates over the stdio transport, making it
usable from any MCP-compatible host without host-specific code. The
complete source code is released as open source under the Apache
License~2.0~\parencite{mcp-server-rhoai-repo}.

The five goals stated in Section~\ref{sec:motivation} have been met.
The server provides \textbf{full workbench lifecycle coverage} through
20~tools covering five resource domains: workbenches, notebook images,
hardware profiles, persistent storage, and namespaces.
\textbf{Resource consumption monitoring} is available at four
granularities --- per workbench, per namespace, per user, and
cluster-wide --- giving both data scientists and administrators
visibility into how compute resources are allocated.
\textbf{Safety by default} is enforced at the registration level: the
server starts in read-only mode and only exposes write tools when
explicitly enabled via the \texttt{-mode} command-line flag or an
environment variable, so that unregistered tools are never advertised to
the host. \textbf{Quality assurance} is covered by unit tests that use
centralised fake-client helpers to validate every tool domain against a
simulated cluster, and by an automated Promptfoo evaluation comprising
22~test cases that achieved a 100\% pass rate with Gemini~2.5~Pro ---
verifying both tool selection and parameter extraction. The iterative
evaluation process also helped refine tool descriptions for better
cross-model compatibility. Finally, the server \textbf{exercises all three
MCP primitives} --- tools, three resources (Image Catalog, Hardware
Profiles, and Namespaces), and a Create Workbench prompt --- demonstrating
how they can all work together in a guided workflow.

Because RHOAI is transitioning from the current Kubeflow-based
workbench architecture to Notebooks~2.0 --- a redesigned notebook
subsystem described in the following section --- the implementation
presented in this thesis is best understood as a proof of concept. It
demonstrates that managing OpenShift~AI workbenches through natural
language via MCP is both feasible and practical, and establishes the
architectural patterns, tool design, and evaluation methodology that a
future production-ready server can build upon. Once Notebooks~2.0 is
integrated into RHOAI, the server will need to be restructured to
target the new API surface, but the core design decisions --- the
two-mode safety model, the package separation, and the MCP-level
infrastructure --- are independent of the underlying CRD and can be
carried forward.

\section{Future Work: Notebooks 2.0}
\label{sec:future-work}

Kubeflow Notebooks~2.0, officially called \textit{Kubeflow
Workspaces}~\parencite{notebooks-v2}, is a complete redesign of the
notebook subsystem that is expected to be integrated into RHOAI later
this year. The redesign replaces the single
\texttt{Notebook} CRD (\texttt{kubeflow.org/v1}) with two new custom
resources under the API group
\texttt{kubeflow.org/v1beta1}~\parencite{notebooks-v2-design}: a
namespaced \texttt{Workspace} resource that end users create, and a
cluster-scoped \texttt{WorkspaceKind} resource that administrators
define as a template. When creating a \texttt{Workspace}, users
select a \texttt{WorkspaceKind} (e.g.\ \enquote{jupyterlab},
\enquote{vs-code}), an approved image configuration, and a pod
configuration (e.g.\ \enquote{small\_cpu}, \enquote{big\_gpu}) from
options defined by the administrator in the \texttt{WorkspaceKind};
they no longer need to specify low-level Kubernetes details such as
container image URLs, resource requests, or volume mount paths.
Metadata that the current architecture stores as RHOAI-specific
annotations --- image display names, hardware profile references,
workbench ownership, and the stopped/running state --- moves into
structured spec and status fields. The status model is also richer:
instead of the current binary running/stopped distinction, a
\texttt{Workspace} reports one of six states (\texttt{Running},
\texttt{Paused}, \texttt{Pending}, \texttt{Terminating},
\texttt{Error}, \texttt{Unknown}). Additional new features include
built-in activity culling with configurable probes, deferred updates
that let administrators redirect old image or pod configurations to new
ones without breaking existing workspaces, and explicit separation of
home and data volumes in the \texttt{Workspace} spec.

Adapting the MCP server to Notebooks~2.0 would require changes in
three main areas. First, the workbench tools would need to target the
new \texttt{Workspace} CRD instead of the current \texttt{Notebook}
CRD --- reading structured spec fields rather than parsing annotations,
and creating workbenches by referencing \texttt{WorkspaceKind} option
identifiers rather than constructing full Kubernetes manifests.
Second, image and hardware profile management would change most
significantly, because approved images and compute profiles are no
longer separate resources (ImageStreams and HardwareProfiles) but
entries defined inside \texttt{WorkspaceKind} objects. Third, the MCP
resources and the Create Workbench prompt would need to query
\texttt{WorkspaceKind} resources as their data source. On the other
hand, the tool registry, the two-mode safety design, the MCP-level
infrastructure, the evaluation framework, and the overall project
structure can all remain unchanged. Notebooks~2.0 could also enable
entirely new MCP tools --- for example, listing available
\texttt{WorkspaceKind} definitions or querying workspace activity and
idle status.
